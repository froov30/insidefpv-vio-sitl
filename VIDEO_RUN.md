# Task 2 video evidence

This file documents how the takeoff/hover/landing video was produced, how to
reproduce it, and how to check that the file is real footage rather than an
artefact.

## The recorded file

| | |
|---|---|
| Video | `results/task2/video_20261120_011831/takeoff_land.mp4` |
| Position log | `results/task2/video_20261120_011831/flight.csv` |
| Summary | `results/task2/video_20261120_011831/flight.summary.json` |
| Resolution / rate | 640x480, 10 fps, 381 frames, 38.1 s |
| Flight | climb to 5.06 m, 8 s hover, land, disarm, 33.8 s of autopilot time |
| Captured | 2026-11-19T19:48:54Z to 19:49:41Z |

The video and the CSV come from **one** run: `takeoff_land.py --video`
subscribes to the camera and starts recording before it sends the arm
command, and it closes the file after the landing check. The frame count is
also stored in `flight.summary.json` (`video_frames`), so the mp4 can be tied
to the log that describes the same flight.

The view is the aircraft's own gimbal camera, pitched 0.7 rad down. The
runway fills the frame at the start, the aircraft's shadow moves away as it
climbs, and the ground grows again on the way down. The checkerboard field
on both sides of the runway is the calibration target set that
`worlds/vio_runway.sdf` adds for Task 3.

## How it was recorded

Headless, no desktop session required. Gazebo is started server-only but
with rendering enabled, so the camera sensor still produces frames - this is
the same mode the automated test uses.

```bash
# Terminal 1: Gazebo + ArduCopter SITL. Stays in the foreground; Ctrl-C
# stops both, and it kills stale processes on the way in.
bash scripts/run_sim.sh --headless

# Terminal 2: fly the profile and record the camera.
RUN=results/task2/video_$(date +%Y%m%d_%H%M%S)
mkdir -p "$RUN"
python3 scripts/takeoff_land.py \
    --log "$RUN/flight.csv" \
    --video "$RUN/takeoff_land.mp4" \
    --gimbal-pitch 0.7
```

`--gimbal-pitch 0.7` points the camera down so the ground, not the sky,
fills the frame; without it the camera looks level and the takeoff is much
harder to see. `--video` is optional, so the automated test
(`scripts/test_task2.py`) still runs without Gazebo transport in the loop.

## How to verify the file

Nothing here is asserted from memory; both checks read the recorded file.

```bash
python3 - <<'PY'
import cv2
cap = cv2.VideoCapture("results/task2/video_20261120_011831/takeoff_land.mp4")
print("frames", int(cap.get(cv2.CAP_PROP_FRAME_COUNT)),
      "fps", cap.get(cv2.CAP_PROP_FPS),
      "size", int(cap.get(cv2.CAP_PROP_FRAME_WIDTH)),
      "x", int(cap.get(cv2.CAP_PROP_FRAME_HEIGHT)))
PY
```

Expected, and what this run actually printed:

```
frames 381 fps 10.0 size 640 x 480          # 381 / 10 = 38.1 s
```

A black or single-colour video still reports a frame count, so the second
check is that the pixels change. Frame brightness (OpenCV `frame.mean()`,
0-255) for this run was 75.4 at the start, 114.0 mid-flight and 76.1 after
landing: the frame gets brighter when the ground fills it at altitude and
dims again on touchdown. A constant value across the three frames would mean
the camera never rendered.

```bash
ffprobe results/task2/video_20261120_011831/takeoff_land.mp4   # if installed
```

`ffprobe` is not installed on the machine that produced this run, so the
OpenCV check above is what was actually used.

## Recording the Gazebo window instead (optional)

A desktop recording shows the world view and the Gazebo UI as well, which is
a useful complement but not a substitute: it needs a graphical session, so it
cannot be regenerated by the automated test. With `ffmpeg` available:

```bash
bash scripts/run_sim.sh                     # windowed, no --headless
ffmpeg -f x11grab -framerate 30 -video_size 1920x1080 \
       -i "$DISPLAY" -c:v libx264 -pix_fmt yuv420p -t 60 \
       results/task2/desktop_capture.mp4
python3 scripts/takeoff_land.py --log results/task2/desktop_capture.csv
```

Neither `ffmpeg` nor OBS is installed here, so this path was **not** executed
and no desktop capture is claimed. The camera recording above is the video
evidence that exists.

## Why the camera and not GStreamer

The camera frames are read with the gz-transport Python bindings
(`scripts/camera.py`), the same API Task 3 uses for the dataset. Gazebo can
also stream the camera over GStreamer on UDP 5600, but that needs a pipeline
to be configured and decoded on the other side, and it is a second, different
transport to debug. The gz-transport route is one dependency, no ROS, and it
records the same frames the VIO will consume.
